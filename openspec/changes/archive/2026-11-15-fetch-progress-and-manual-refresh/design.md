## Context

動機見 `proposal.md`。這裡只列影響做法的現況（2026-11-14 讀程式所得）：

- 抓取排程在專屬執行緒跑（`host/src/fetch/scheduler.rs` 的 `run_loop`／`tick`）：每次醒來問 `sched::Scheduler::step`
  要不要開始一輪，睡眠用 `StopSignal::wait`（condvar，可被停止要求打斷）。一輪經 `SchedEnv::run_round` 執行，外部依賴
  全部由 `SchedEnv` 注入，測試以假環境推進假時鐘。觸發種類 `sched::Trigger`＝`FirstFetch`／`Slot`／`Missed`／`Retry`。
- 一輪實測約 33–49 秒（12 個來源循序、同主機間隔 2 秒；等網路最長另加 300 秒）。
- 排程對外沒有「進行中」狀態。設定視窗的 `get_fetch_status` 讀 `fetch-state.json` 與資料檔，開窗時查一次。
- 資料進到小工具的路徑：抓取寫 `tw_events.json` → `main.rs` 的資料輪詢執行緒每 30 秒呼叫
  `widgets::poll_and_notify_settled` 比對檔案 → 經 `ipc::Channel` 推快照。
- 小工具外殼 `host/ui/widget.html` 負責訂閱、初始化競態、編輯版面與內容回報；各小工具模組（`widgets/<id>.js`）只管畫內容。
  外殼以 `ResizeObserver` 量內容大小、呼叫 `report_content(hasContent)`，核心據此顯示或隱藏視窗——行情條無資料時內容高度
  為 0，所以視窗被隱藏。
- 廣播事件的既有慣例（`edit-mode`、`pause`、`widget-font`）：非敏感 UI 狀態用事件；頁面先 `listen` 再查詢，查詢在途期間
  收到的事件優先。資料本體只走 `ipc::Channel`。本機自訂指令沒有逐指令 ACL，限制靠指令自己檢查呼叫端 webview label。
- 2026-10-12 曾談過一版較細的設計（逐來源進度「第 N/12 項：來源名」）。使用者 2026-11-14 定案的畫面只有動畫與
  「資料抓取中…」，本設計採較小的狀態模型，逐來源進度列為 Non-Goal。

## Goals / Non-Goals

**Goals:**

- 使用者任何時候都看得出宿主正在抓資料，且看得出抓完了。
- 手動更新走排程執行緒同一條路，不另開第二個會寫資料檔的執行緒。
- 沒有抓取進行時，小工具的 DOM 與畫面和現在相同（與 Lively 版對照測試不受影響）。

**Non-Goals:**

- 逐來源進度（第幾項、來源名稱）、進度百分比、預估剩餘時間。
- 「部分來源失敗時提早重試」（Backlog 另列）。
- 擴充插槽、動態桌布、系統匣選單的更新入口。
- 設定視窗圖示與小工具上的新版提示（橘點只畫在系統匣圖示）；改變自動安裝或通知的時機。
- 手動更新的冷卻時間（見 Risks）。

## Decisions

### D1 狀態模型：一個小的活動狀態，事件廣播＋查詢

狀態 `FetchActivity { running: bool, enabled: bool, last: "none" | "ok" | "failed" }`，由排程執行緒寫、存在
Tauri managed state（`Mutex`），改變時廣播事件 `fetch-activity`（payload 即整個狀態），並提供查詢指令
`get_fetch_activity`。

- `running`：`tick` 決定開始一輪到該輪結束（含等網路、含被中止）之間為真。
- `enabled`：`decide_gate` 的結果是否為 `Gate::Enabled`；閘門改變時更新。
- `last`：行程內最近一輪的結果；啟動時由排程紀錄（`fetch-state.json` 的 `last_any_success`）初始化，沒有紀錄＝`none`。
  被中止的一輪不改 `last`。

查詢指令接受小工具視窗（label 以 `w-` 起頭的既有判斷）與設定視窗，其餘 label 回錯誤。

**為什麼用事件而不是 Channel**：內容是非敏感 UI 狀態（三個欄位，不含資料、路徑、代理），與 `edit-mode`／`widget-font`
同類；所有小工具與設定視窗都該收到，沒有「限定收件者」的需求。新事件名加進 `self_test_ipc.rs` 的 `BARE_PROBE_EVENTS`。

**替代方案**：把狀態塞進資料快照的 `meta`。否決——快照只在檔案改變時推送，「開始抓」這一刻檔案沒變；而且會讓
「拒收無效資料、保留上一份好資料」的邏輯多一個維度。

### D2 寫入點：`SchedEnv` 多一個回報方法

`SchedEnv` 加 `fn activity(&self, activity: FetchActivity)`（預設實作為空，既有假環境不必改）。`tick` 在三處呼叫：
閘門改變時、決定開始一輪之前（`running: true`）、一輪結束後（`running: false`，含 `Aborted` 與 panic 被接住的情況）。
正式環境 `HostEnv::activity` 寫 managed state 並 `emit`。排程執行緒 panic 被 `run_loop` 接住時也要送一次
`running: false`，否則圖示會卡在轉圈（以 `LoopState` 記住「上次送出的值」，每次醒來開頭若與應有值不同就補送）。

**結束通知的順序**（對應 `widget-data-feed`「抓取完成後立即更新快照」）：`HostEnv::activity` 在 `running` 由真變假時，
先同步呼叫一次 `widgets::poll_and_notify_settled`（與資料輪詢執行緒同一個函式），再 `emit`。這只保證後端的呼叫順序；
頁面實際收到的順序可能相反，由小工具外殼補上（見 D8）。兩條執行緒可能同時輪詢：動手前先確認
`ChannelRegistry::poll_all_changed` 在鎖內完成比對與更新（讀程式確認；若不是，改成對資料輪詢執行緒送喚醒訊號並等它跑完）。
桌布協調迴圈的 `Wake::DataChanged` 通知照資料輪詢執行緒的做法一起發。

### D3 手動更新：旗標＋喚醒，進同一個迴圈

`StopSignal` 旁邊加一個「手動要求」旗標，共用同一個 condvar（把 `StopSignal` 擴成同時帶 `stopped` 與
`manual_requested` 兩個旗標的喚醒訊號；`wait` 在任一旗標成立時提早返回，回傳值仍只表示是否要停止）。

- 指令 `request_fetch_now`（只收設定視窗 label，比照 `require_settings_window`）：
  - 閘門不是 `Enabled` → 回 `{ outcome: "disabled" }`，不設旗標。
  - 活動狀態 `running` 為真 → 回 `{ outcome: "already_running" }`，不設旗標。
  - 否則設旗標並喚醒 → 回 `{ outcome: "started" }`。
  - 沒有排程把手（啟動失敗、正在因更新結束）→ 回錯誤。
- `tick`：閘門為 `Enabled` 時先取走旗標；有就直接以新的 `Trigger::Manual`（記錄字串 `manual`）開始一輪，不經
  `Scheduler::step` 的時點與下限判斷。閘門不是 `Enabled` 時取走並丟棄。
- 一輪結束時再清一次旗標：抓取進行中送來的要求由這一輪吸收，不會緊接著再抓一輪（指令那一端已先擋，這裡收掉
  「檢查與設旗標之間剛好開始一輪」的空隙）。
- 手動那一輪照常寫排程紀錄（`FetchState::after_round`），所以之後的時點與補抓以它的開始時間計算 60 分鐘下限。
  手動輪失敗同樣走既有的重試退避。

**替代方案**：指令自己開執行緒跑 `run_scheduled_round`。否決——會有兩個執行緒可能同時寫資料檔與排程紀錄，
也繞過停止流程（系統匣結束、因更新結束都只停排程執行緒）。

### D4 小工具：外殼統一處理，模組只改無資料文字

外殼（`widget.html`）訂閱 `fetch-activity`（先 `listen` 再 `get_fetch_activity`，沿用 `widget-font` 的初始化寫法：查詢在途
期間收到的事件優先），擴充插槽不訂閱。

- **角落圖示**：外殼在 `#widget-root` 之外加一個固定定位的元素，只在 `running` 為真且不是整塊載入時顯示。
  `pointer-events: none`、放在右上角內距內、尺寸約一個字高、低對比。編輯版面時右上角是 A−／A+ 控制，圖示改放左上角
  或暫時不顯示（實作時擇一，以不重疊為準）。元素不在內容容器內，所以不影響 `ResizeObserver` 量到的內容大小、
  不影響捲動、不影響收合版面的量測。
- **整塊載入**：`registry.js` 的財經小工具項目加布林欄位 `needsData`（總經日曆、台股動態事件、行情條為真）。
  外殼判斷 `loading = needsData && 目前快照不是 ok && enabled && (running || last === "none")`。成立時把內容容器隱藏、
  顯示外殼自己的載入區塊（動畫＋「資料抓取中…」），並以 `report_content(true)` 回報有內容，行情條視窗因此保持可見。
  條件解除時還原，交回 `ResizeObserver` 的正常回報。`last === "none"` 那一項涵蓋「宿主剛啟動、首抓還沒開始」的
  十幾秒。
- **無資料文字**：外殼把活動狀態放進 `ctx`（`ctx.fetchActivity()` 取目前值、`ctx.onFetchActivity(fn)` 訂閱）。
  三個需要資料的模組在快照不是 ok 且不在整塊載入時，依 `enabled`／`last` 選文字（規格見 `widget-data-feed`「尚無資料」）。
  文字集中在 `common.js` 的一個純函式，三個模組共用，測試直接測它。
- **減少動態效果**：動畫用 CSS，`@media (prefers-reduced-motion: reduce)` 內關掉 `animation`，圖示改成靜止的同一個圖形。
- **動畫本身**：純 CSS 的旋轉圓弧（`border` 圓環＋`transform: rotate`），不引入圖片或套件；只動 `transform`，
  不觸發版面重算。暫停狀態（`pause` 事件）下一併停止動畫，與行情條跑馬燈的做法一致。

`registry.js` 既有的一致性測試只比 id 與通道、並斷言沒有版面欄位；`needsData` 不是版面欄位，測試的斷言清單要確認不會擋它。

**替代方案**：每個小工具模組各自畫動畫。否決——五份重複，而且時鐘與固定事件沒有「無資料」分支可掛。

### D5 設定視窗

`settings.html` 訂閱 `fetch-activity`：`running` 變化時更新按鈕，`running` 由真變假時重跑 `refreshFetchStatus()`。
開頁時查一次 `get_fetch_activity` 決定按鈕初始狀態。按鈕與文字的對應（放進 `settings-fetch.mjs` 的純函式，方便測試）：

| 狀態 | 按鈕 | 狀態文字 |
| --- | --- | --- |
| `enabled` 且未在抓 | 「立即更新資料」，可按 | 既有的上次更新時間與成敗 |
| `running` | 「更新中…」，停用 | 既有文字前加「更新中…」 |
| 未啟用（off／隔離） | 「立即更新資料」，停用 | 既有的「未抓取」原因 |

按下後呼叫 `request_fetch_now`；回 `started`／`already_running` 都靠隨後的事件更新畫面，回 `disabled` 或錯誤時在狀態區
顯示一行說明。

### D6 文案

- `dynamic.js` 過期提示：「請檢查工作排程」改為指向設定視窗的「立即更新資料」。
- `settings.html` 資料目錄提示：拿掉「指向 update_tw_events.py 的輸出資料夾」，改述資料目錄的用途；指向別的程式的輸出
  資料夾前要先關閉抓取這件事，寫在提示裡。
- `macro.js` 無資料文字改走 D4 的共用函式。

### D7 系統匣圖示的新版橘點

- **條件**：與系統匣選單出現「更新到 vX.Y.Z 並重新啟動」同一個來源——`updater` 的待安裝版本（`ready_version()` 有值＝
  新版已下載並驗簽、等使用者手動安裝）。登入後 10 分鐘內自動安裝的情況不會經過這個狀態，行程直接重新啟動，不顯示橘點。
- **畫法**：執行期在選定尺寸的 RGBA 上疊圖，不新增圖示檔（六套圖示×七個尺寸，逐張產製要多 42 個檔，且 `make-icons.mjs`
  與 `.ico` 逐位元組核對的測試都要跟著改）。`app_icon.rs` 加純函式：輸入 RGBA 與邊長，在右下角畫實心橘色圓，直徑約為
  邊長的 45%（16px 時 7px），外圈一圈深色描邊。描邊是必要的：統一產品圖示本身是金色，橘點直接疊上去對比不足。
- **去重紀錄**：系統匣目前以（圖示組、尺寸）去重；加入「是否帶橘點」，否則待安裝狀態改變時會被當成沒變而略過。
- **提示文字**：有待安裝版本時系統匣提示文字為「財經日曆（有新版 vX.Y.Z）」，否則為「財經日曆」。與圖示在同一次套用裡設定。
- **觸發**：`updater.rs` 的 `notify_ready` 與 `refresh_menu`（待安裝的更新被安裝失敗丟棄時會呼叫）在重建選單的同時呼叫
  `app_icon::request_refresh`。橘點狀態不由呼叫端傳入，而是套用前在 `refresh_in_order` 讀最新的待安裝版本，與主題的讀法
  一致，順序保證沿用既有的 `REFRESH_ORDER`。explorer 重新啟動、縮放改變、主題切換等既有刷新路徑自動帶上橘點。
- **只畫系統匣**：設定視窗圖示不加。設定視窗開著時使用者本來就在看宿主的介面，工作列按鈕上的橘點也容易被誤認成未讀通知。

### D8 結束通知與新快照的送達順序由頁面保證

第 1 組審查發現（2026-11-15）：後端「先輪詢、後廣播」只保證呼叫順序。Tauri 的 `Channel::send` 對 8192 bytes 以上的 JSON
不直接送達，而是讓頁面再發一次 IPC 取回（`tauri` 的 `ipc/channel.rs`，`MAX_JSON_DIRECT_EXECUTE_THRESHOLD`）；`fetch-activity`
事件則是直接送達。`tw-events` 快照遠大於這個門檻，所以頁面實際上先收到「沒有抓取進行中」、隔一次 IPC 來回才拿到快照。

規格「抓取完成後立即更新快照」的 MUST（結束通知不早於新快照）因此由小工具外殼補上：收到 `running` 由真變假、
且小工具需要資料而手上沒有有效快照時，外殼先維持載入狀態並主動查詢一次快照（後端此時已有新快照），拿到回覆
（有資料或確定沒有）之後才離開載入狀態。查詢失敗或逾時（2 秒）時照當下狀態顯示。已有資料的小工具不受影響：角落圖示直接消失，
新資料稍後到達時照常重繪。

查詢活動狀態失敗（例如排程尚未登記）時，外殼把狀態當成「未知」：不顯示載入、不顯示失敗文字以外的新提示，等第一筆
`fetch-activity` 事件校正（排程第一次醒來一定會送）。

## Risks / Trade-offs

- [角落圖示每天至少五次、每次轉 33–49 秒，可能讓人分心] → 圖示做小、低對比、不改版面；使用者已知悉並同意
  （2026-11-14）。若實機覺得太干擾，退路是只在手動更新與無資料時顯示，改一個條件即可，不動架構。
- [手動更新沒有冷卻，連按可以每四十秒打一輪來源] → 進行中不能重複觸發，人為連按的頻率上限就是一輪的長度；
  同主機 2 秒間隔仍然有效。若日後出現被來源限流的證據再加冷卻。
- [排程執行緒在輪中 panic 或被中止，`running` 沒有歸零，圖示永遠轉] → D2 的補送機制；測試覆蓋「輪 panic」
  「輪被中止」「閘門在輪中關閉」三種結束路徑都送出 `running: false`。
- [結束時同步輪詢與資料輪詢執行緒併發] → D2 已要求先確認鎖的範圍；測試以兩條執行緒同時呼叫驗證只推送一次新快照
  或推送兩次相同世代（頁面已會濾掉重複）。
- [整塊載入時強制回報有內容，條件解除後忘了交回正常回報，行情條無資料卻一直顯示空視窗] → 條件解除時立即依當下
  量到的大小重報一次；前端測試覆蓋「載入 → 失敗仍無資料」後回報為無內容。
- [與 Lively 版對照測試] → 沒有抓取進行、且有資料時外殼不新增任何可見節點；`compare.mjs` 在這個條件下跑，結果應不變。
  無資料文字改了的部分若對照測試有涵蓋，列為刻意差異。
- [16px 圖示上再疊一個 7px 的點，主題圖示的右下角細節被蓋住] → 橘點只在有待安裝版本時出現，屬暫時狀態；
  實機在 100% 與 150% 縮放各看一次，太擠就把直徑比例調小（一個常數）。
- [更新流程的收尾期間刷新圖示] → `request_refresh` 只讀狀態與換圖示，不建視窗、不寫檔；沿用既有路徑，
  系統匣設定失敗的延後重試也已存在。
- [事件在視窗建立初期漏接] → 沿用「先 listen 再查詢」；另外事件 payload 是完整狀態而非差異，漏一筆下一筆就校正。

## Migration Plan

沒有資料或設定的遷移。新版啟動時活動狀態由排程紀錄初始化；舊版留下的 `fetch-state.json` 欄位不變。
回退到舊版不需要任何處理。
