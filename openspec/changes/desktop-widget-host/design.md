## Goals / Non-Goals

**Goals:**

- 宿主核心與小工具頁面之間只透過「通道快照查詢＋事件推送」溝通；子專案 2 換資料來源、日後擴充
  插槽接新資料源時，核心、視窗管理與設定結構都不需修改。
- Win32 相關行為集中在單一模組，其餘程式碼不直接呼叫 Win32。
- 財經小工具的顯示邏輯從 Lively 版**搬移而非重寫**，並以對照測試證明結果一致。

**Non-Goals:**

- 不做第三方小工具安裝機制或外掛市集；擴充插槽只供本專案日後自行實作。
- 不做多組版面切換、雲端同步設定。
- 不支援 Windows 10 以前版本；Windows 10 可執行但只有純色模式（不另外測試其他差異）。
- 不使用未公開 API（例如 `SetWindowCompositionAttribute`）實作毛玻璃。

## Decisions

### D1. 每個小工具一個 WebView2 視窗，共用同一個 WebView2 環境

- 選擇：每個開啟的小工具一個 `WebviewWindow`，同一個 user data folder（共用 browser process）。
- 理由：Acrylic 與圓角是視窗層級屬性，一個小工具一個視窗就能直接套用；面板之外天然可點穿；
  拖曳只是移動視窗。
- 替代：單一透明大視窗＋`SetWindowRgn` 裁形——Acrylic 與不規則區域能否並存未驗證，且拖曳要
  自己做命中測試，捨棄。

### D2. 小工具頁面嵌入 exe，從 Tauri 內建來源載入

- 選擇：`host/ui/` 為 `frontendDist`；spike 的自訂 `fc` scheme 與命令列參數移除。
- 理由：資料改走 IPC 後頁面不需讀磁碟；頁面嵌入 exe 可避免使用者修改前端造成版本不一致。
- 替代：保留 `fc` scheme 讓頁面讀資料目錄——頁面會與磁碟格式耦合，違背 Goals 第一條。

### D3. 權限與前端取得 Tauri API

- `host/capabilities/default.json`：適用所有小工具視窗與設定視窗，權限為 `core:default` 加
  `core:window:allow-start-dragging`、`core:window:allow-start-resize-dragging`（編輯版面調整
  大小，見 D7；名稱查自 `tauri-2.12.0/permissions/window/autogenerated/reference.md`）。開機自啟
  由後端直接寫登錄（見 D12），不開放頁面呼叫。
- `tauri.conf.json` 設 `app.withGlobalTauri: true`，頁面以 `window.__TAURI__` 呼叫，無需打包工具。
- 驗收一律在 release build（無 devtools 例外）下實測。

### D4. 核心→頁面介面（通道化）

- 查詢：`get_snapshot(channel) -> { channel, status: "ok"|"empty", data, meta, generation }`，
  `meta` 含 `loadedAt`；通道 `tw-events` 另含 `fetched`、`updated`。`generation`＝通道註冊表
  世代（`ok` 與 `empty` 都帶）：修改資料目錄會整份重建註冊表並遞增世代，重建後的 `empty`
  比重建前的任何快照都新。
  `get_settings() -> Settings`、`get_pause() -> { paused, reason }`（目前暫停狀態；`pause`
  事件只在變化時廣播，頁面啟動或重新載入時須以此取得初始狀態）、`get_edit_mode() -> bool`
  （目前是否在編輯版面；理由同 `get_pause`）、`update_settings(patch)`、
  `set_edit_mode(bool)`、`report_content(has_content)`（頁面回報有無可顯示內容，見 D7）。
- 資料推送：頁面呼叫 `subscribe_data(onData: Channel)`，核心依**發出請求的 webview label**
  決定其訂閱通道，之後以該 `tauri::ipc::Channel` 推送 `{ channel, generation, snapshot }`
  （`generation` 同上，取快照當下的註冊表世代）。不用 Tauri 事件投遞資料：`emit_filter`／`emit_to` 依監聽者自行宣告的 target 過濾，頁面以預設
  `event.listen`（target＝Any）即可繞過，無法保證「只送給訂閱該通道的視窗」。
  `snapshot` 可為 `null`：改資料目錄整份重建通道註冊表後（見上方 `get_snapshot`），核心對
  當時已訂閱的每個通道各推一筆 `{ channel, generation, snapshot: null }`（新世代、`null`
  即該世代的 empty），已開啟的小工具因此立刻改顯示「尚無資料」，不必等到（若曾經）新目錄
  出現有效檔案才更新，也不會停留在切換前的資料；之後新目錄若出現有效檔案，照常以同一世代
  推送 `ok` 快照。
- 事件：`settings`（完整新設定）、`pause`（`{ paused, reason }`）、`edit-mode`（`bool`）、
  `edit-preview`（`{ id, valid }`，編輯版面拖曳中「若此刻放開」的合法性改變時廣播，頁面只理會
  `id` 等於自己的那筆，用來切換紅色外框；不含資料，廣播即可）。
- 每個小工具在註冊表宣告訂閱的通道（財經小工具＝`tw-events`，`customN`＝`customN`）。
- 頁面啟動順序：先 `listen` 全部事件並 `subscribe_data`，再呼叫 `get_snapshot`／`get_settings`／
  `get_pause`／`get_edit_mode`，避免兩者之間漏掉事件；查詢仍在途時收到的事件優先（`data` 依
  `(generation, meta.loadedAt)` 比較：世代較新者勝，同世代才比 `loadedAt`，此時 `empty` 才視為
  最舊；掛載後世代較舊的推送一律丟棄。`settings`／`pause`／`edit-mode` 沒有版本欄位，掛載前收到過事件就以
  事件為準）。
- 理由：推送「完整快照」而非差異，頁面無須合併邏輯，重連即重拿。

### D5. 資料來源抽象與通道註冊表

- Rust trait `DataSource`（`poll() -> Option<Snapshot>`），通道註冊表把通道名對應到來源實例。
- 本 change 實作 `JsonFileSource { path, validator }`：每 30 秒比對修改時間＋檔案大小，有變才
  讀取、解析、驗證，通過才替換快照並推送。`tw-events` 的 validator 移植 `isEmptyPayload`
  判準；`customN` 的 validator 只要求為合法 JSON。
- 資料目錄預設 `%LOCALAPPDATA%\tw.fintools.fc-host\data`，可在設定修改。
- 新增資料源的路徑：在註冊表加一行通道（或沿用 `customN`）＋一個 `DataSource` 實作；
  子專案 2 的 `FetchSource` 走同一條路。

### D6. 小工具註冊表與擴充插槽

- 前端 `widgets/registry.js` 列出十個小工具的 `id`、訂閱通道、顯示模組。格線模型下頁面只是
  填滿視窗，不需要知道任何尺寸，因此版面欄位（設計寬度＝倍率 1 時的邏輯寬度、設計最小高度、
  預設格座標 `{ col, row, w, h }`、預設開關）只放在 Rust 端（`widgets.rs` 的規格表與
  `settings.rs` 的預設值；設定與視窗管理只依 `id` 運作，不認得小工具內容）。一致性測試只比對
  兩端的 `id` 與通道，另斷言十個預設格座標兩兩不相交。
- `widgets/customN.js` 為空白模組：無資料顯示「尚未設定」，有資料顯示更新時間與內容摘要
  （頂層鍵與筆數）。日後接新資料源時只替換此檔。

### D7. 格線版面與小工具尺寸

2026-09-30 取代原本「固定寬度＋高度跟隨內容＋錨點距離」的模型。原模型把 Lively 版單頁流式
排版拆成獨立視窗後，相鄰視窗只能用鄰居的估計或上限高度推位置，內容一長或螢幕一小就重疊
（B4 代驗實例、以及 dynamic 在小螢幕蓋住行情條）。新模型讓每個小工具都有明確的格子矩形，
重疊在推導階段就被排除，不靠估計。

- 格線：每個顯示器工作區切成 `GRID = 48` 欄 × 48 列。格線 `i` 的實體像素座標為
  `edge(i) = 工作區起點 + floor(i × 工作區實體長度 / 48)`（整數運算）。小工具矩形為
  `[edge(col), edge(col+w)) × [edge(row), edge(row+h))`，因此共用格線的兩個小工具在該邊落在
  同一個像素，不重疊也不留縫；彼此間要留空隙就空一格。工作區實體長度 ≥ 48 時
  `round((edge(i) − 起點) × 48 / 長度) = i`，對齊可精確還原格線編號。
- 尺寸：視窗矩形＝格子矩形，不隨內容改變。倍率
  `zoom = clamp(矩形邏輯寬 / 設計寬度, 0.5, 3.0)`（邏輯寬＝實體寬 ÷ 該顯示器縮放比例），沿用
  WebView2 ZoomFactor 套用（`layout::content_zoom` 改為由矩形計算）。未夾住時頁面 CSS
  viewport 寬＝設計寬度、高＝矩形邏輯高 ÷ zoom；頁面以 100% 視窗高度排版、清單區捲動——視窗
  大小已固定，不再有「內容決定高度、高度又決定內容」的循環，`vh` 可以恢復使用。夾住時：
  超過 3 倍的部分頁面撐寬填滿；不足 0.5 倍（顯示器變小所致）時格座標不自動改，右側內容被裁切。
- 最小格數（依顯示器當下工作區計算，非常數）：寬格數為讓 zoom 達到 0.5 的最小值；高格數為讓
  矩形邏輯高度 ≥ 設計最小高度 × 該寬度下的 zoom 的最小值。編輯版面的拖曳預告、放開與找空位
  都用同一個判斷。倍率只看寬度而格高跟著螢幕高度走，所以寬螢幕（高寬比小）的可用設計高度較少；
  預設格座標以「高寬比 ≥ 0.53 的工作區都不小於最小格數」為準，由屬性測試守住。設計最小高度
  是整扇視窗的 CSS 高度，含 `#widget-root` 上下兩個 `--widget-gap`（fix min-height：面板內容
  最小高度＋16），設計寬度不含 gap（`widgets.rs` `WIDGET_SPECS` 註解記理由）。
- 無內容：頁面以 `report_content(has_content)` 取代 `report_size`，核心據此隱藏／顯示視窗，並
  在處理時重套一次倍率（取代 `report_size` 原本「頁面 Reload 後 ZoomFactor 可能回到 1」的保險，
  見 `widgets.rs` 相關註解）。隱藏中的小工具格子照樣保留，碰撞與找空位都算它；編輯版面期間
  核心顯示所有開啟中且有格子的小工具（因空間不足暫時隱藏者沒有格子，不顯示），無內容者由頁面畫佔位外框。
- 碰撞：純函式判斷格子兩兩不相交且都在 `0..=48` 內，`w、h ≥ 1`。
- 找空位：候選左上角的列 `row` 由 0 往下、同一列的欄 `col` 由 `48 − w` 往 0（右上優先），
  第一個不相交的候選即採用；先試記錄格數（從未開啟過者即預設格數），失敗再試最小格數。
- 記錄位置的寫回時機只有兩個，都是使用者操作：
  1. 編輯版面放開成功：立即寫回該小工具（沿用現行每次放開即存檔，當機不遺失）；原本暫時換位
     的小工具也一樣，記錄改到放開所在的顯示器。
  2. 開啟小工具：所屬顯示器存在，且記錄格子與記錄就在該顯示器上的其他開啟中小工具的**記錄位置**相交
     時，找空位並寫回；找不到則 `update_settings` 回傳錯誤，設定視窗顯示「空間不足，請先調整
     版面」並把開關還原。所屬顯示器不存在時不找空位、不寫回，交給 D9 推導暫時換位。
  `update_settings` 拒收 `placement` 欄位（版面只能經上述兩條路徑改）。
- 編輯版面（Win32 部分在 `desktop` 模組）：
  - 移動沿用 `startDragging`（`data-tauri-drag-region`）。
  - `WM_MOVING`／`WM_SIZING` 以提議矩形算出「若此刻放開」的對齊結果與合法性，合法性改變時廣播
    `edit-preview`；`WM_EXITSIZEMOVE` 依相同計算，合法就寫回記錄、重新推導並把視窗設到推導
    結果，不合法就把視窗設回推導出的原矩形（拖曳前矩形即推導結果，不另存）。
  - 合法條件：對齊後的格子不與其他小工具的**實際位置**相交，也不與**記錄就在該實體顯示器上**的
    其他開啟中小工具的**記錄位置**相交（從別處換來者與暫時隱藏者的記錄不算，否則看似空白處也會
    被擋），且在範圍內；調整大小另要求不小於最小格數。第二個條件保證放開成功者（此後成為該顯示器的原生者）的
    記錄在 D9 推導第一階段永遠不衝突：顯示器組態不變時，重新推導或重啟後位置不變。
  - 移動不檢查最小格數（fix F6，2026-10-02 controller 決定）：移動保留格數、不改大小，檢查
    最小格數只會擋住「記錄格數已小於目前最小格數」的小工具。例如 fix min-height 把設計最小
    高度加上 gap 之後，既有設定裡 16×9 的時鐘在 4K＠150% 低於新的最小格數，若移動也檢查，
    放到哪裡都會彈回。不做設定遷移；這類小工具照舊以記錄格數推導、照樣可以移動，要變大由使用者
    調整大小（調整大小仍檢查最小格數）。跨到縮放比例較高的小螢幕時，保留的格數也可能小於該台的
    最小格數，同樣允許。
  - 對齊：移動保留 `{w, h}`，只對左上角 `round`；所屬顯示器取矩形中心所在的顯示器（中心不在
    任何工作區時取最近者）。調整大小只對齊 `WM_SIZING` 的 `wParam`（`WMSZ_*`）指出的被拖邊，
    其餘邊保持原格線。
  - 跨縮放比例拖曳（fix drag-dpi，2026-10-01 使用者決定：保留格數、所見即所得）：原本 tao
    處理 `WM_DPICHANGED` 時維持邏輯尺寸，時鐘從筆電（175%）拖到 4K（150%）看起來約 732×244
    實體 px，放開卻以保留的 16×9 格（4K 上約 1280×391）判斷，「看起來放得下」的地方其實重疊。
    改為移動期間視窗即時等於「目前格數在目標顯示器上的實際大小」：
    - 純函式在 `layout`：`grid_span_size`（格數→實體大小，`floor(格數×工作區長度÷48)`）、
      `grab_fraction`／`rect_at_grab`（拖曳開始記下游標在視窗內的比例位置，換尺寸後游標仍在
      同一比例位置，視窗不會跳離游標）、`resolve_drag_rect`（選目標顯示器）。目標顯示器以
      「候選矩形的中心落在該顯示器上」為自洽：上一個目標仍自洽就沿用，否則取第一台自洽者，
      都不自洽（抓點偏離中心時換尺寸會讓中心跨回原處的窄帶）就維持上一個目標，避免來回跳。
      起始顯示器沿用拖曳開始時的實際大小（不以 floor 重算，免得 1 px 差異觸發 WebView 重設尺寸）。
    - 預告與放開用同一個目標與同一個格數：`layout::check_move_placement_on(目標, 矩形)`；
      `WM_EXITSIZEMOVE` 時顯示器清單與拖曳快照相同就沿用拖曳中的目標，組態已變才退回中心判定。
      目標改變時同步套用新顯示器上的內容倍率（`grid_zoom`）。
    - Win32（`desktop::widget_subclass_proc`，只在拖曳中介入，其餘情況原樣轉交）：
      - `WM_MOVING`：改寫提議矩形。Microsoft Learn「WM_MOVING message」只承諾採用改寫後的
        **位置**（「To change the position of the drag rectangle…」），所以尺寸不同時另以
        `SetWindowPos(SWP_NOZORDER|SWP_NOACTIVATE)` 套用；之後系統移動迴圈只搬位置。
      - `WM_GETDPISCALEDSIZE`：Microsoft Learn：Per-Monitor-V2 頂層視窗在 `WM_DPICHANGED` 之前
        收到，`lParam` 為 in/out `SIZE*`，回 TRUE 時這個大小成為 `WM_DPICHANGED` 的候選矩形，

    的 both 模式跑法也交叉核對過，兩輪結果一致：三輪 Win+D 進出＋一次點桌面，事件涵蓋率
    100%，沒有任何一次要靠 30 秒保險檢查兜底）。「不另設輪詢」不再只是推論，是實測結論。
  - 暫停置底：子類別化 `WM_WINDOWPOSCHANGING`，在 tao 改寫成 `HWND_BOTTOM` 之後，把
    `hwndInsertAfter` 還原為原本的請求值。
  - 插入位置：`hwndInsertAfter` 設為 `GetWindow(桌面視窗, GW_HWNDPREV)`，也就是插在桌面視窗
    正上方；前一個視窗是 topmost 或不存在時改用 `HWND_TOP`。
  - explorer 在進入後 20～60 ms 內會再抬一次 `Progman`：顯示桌面期間只要偵測到桌面又高於小工具，
    就重插一次；之後 5 秒以上 z-order 都沒有變化。
  - 所有一般視窗都最小化時同樣判為顯示桌面，小工具留在桌面之上；任何視窗還原後即恢復置底。
- Acrylic：**探針 1.2 定案為停用**（`host/examples/probe_acrylic.rs`，記錄檔／截圖
  `host/tools/evidence/1.2-*`）。原計畫「Windows 11 以 DWM 系統背景材質＋圓角偏好，優先評估
  Tauri 內建 `effects()`」在查證階段就已改道：查 `tauri-2.12.0/src/vibrancy/windows.rs`，
  `.effects()` 在 Windows 上實際呼叫 crate `window-vibrancy`（其 `apply_acrylic()`／
  `src/windows.rs`）；該 crate 在 build 號 ≥ 22621 時確實呼叫
  `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE, DWMSBT_TRANSIENTWINDOW)`，但 build
  號更舊時會**退回呼叫未公開的 `SetWindowCompositionAttribute`**——AGENTS.md 明文禁止未公開
  API，故探針改為自己直接呼叫 `DwmSetWindowAttribute`，build 號不足直接跳過（不落到未公開
  API），不採用 Tauri 內建 `effects()`。
  - 屬性與列舉值（Microsoft Learn）：
    [`DWMWINDOWATTRIBUTE`／`DWMWA_SYSTEMBACKDROP_TYPE`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)（載明「supported starting with Windows 11 Build 22621」，即
    [`MIN_BUILD_FOR_SYSTEM_BACKDROP`](../../../host/src/desktop.rs) 的一手來源）、
    [`DWM_SYSTEMBACKDROP_TYPE`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwm_systembackdrop_type)（本探針用 `DWMSBT_TRANSIENTWINDOW`，即 Windows 11 設計語言的
    Acrylic）、
    [`DWM_WINDOW_CORNER_PREFERENCE`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwm_window_corner_preference)（`DWMWCP_ROUND`）、
    [`DwmSetWindowAttribute`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmsetwindowattribute)。
  - 探針作法：以 D8 實際會用的視窗組態（`focusable(false)`／`focused(false)`／
    `decorations(false)`／`transparent(true)`／`visible(false)` 建立後
    `SetWindowPos(HWND_BOTTOM, SWP_SHOWWINDOW|SWP_NOACTIVATE|SWP_NOMOVE|SWP_NOSIZE|
    SWP_FRAMECHANGED)`）同時開 A／B 兩扇外觀相同的視窗，A 套 `DWMSBT_TRANSIENTWINDOW`、
    B 顯式套 `DWMSBT_NONE`（控制組，排除「看起來像模糊其實是 WebView2 透明本身」的誤判）；
    用 `AttachThreadInput` 把前景切到另開的記事本（非模擬按鍵／點擊），確認前景不是小工具，
    再以 per-monitor DPI aware（`SetThreadDpiAwarenessContext`）截圖比對 A／B。
  - **實測結果（2026-09-28，Windows 11 build 26200，筆電面板 2560×1600＠175%）**：兩扇窗
    都正確透明無邊框、圓角生效、無黑底、無殘影；但 A（Acrylic）呈現的是**不透明的平面深色
    色塊**，看不到背後桌布內容，與 B（無材質、可清楚看穿背後桌布細節）明顯不同——即 DWM
    確實對 A 做了某種處理（不是完全沒生效），但那個處理**不是即時模糊**，而是把材質攤平成
    純色，與 design.md 風險登記「Acrylic 可能只在視窗取得焦點時呈現」完全吻合（逐像素讀
    `1.2-laptop-closeup-laptop-default.png` 的 A 面板無文字區：整塊同為 RGB(48,50,54)，亮度
    標準差 0）。額外測試：在文件記載的標準訊息 `WM_NCACTIVATE`（非未公開 API）上子類別化、
    對小工具送 `SendMessageW(hwnd, WM_NCACTIVATE, TRUE, -1)` 強制 DWM 用「使用中」方式畫
    非用戶端外觀（不呼叫 `SetForegroundWindow`、不影響真正輸入焦點）：**結果與預設不同**——
    `1.2-laptop-closeup-laptop-forceactive.png` 的 A 面板不再是均勻色塊，可見背後桌布模糊後
    的色彩與輪廓（同一批取樣點為 RGB(52,47,48)／(50,48,48)／(45,46,48)，無文字區亮度
    標準差約 3～4，範圍約 40～54）。這張靜態截圖**不足以證明是即時模糊**（可能是啟用當下
    的一次性合成結果，也未驗證背景變化時是否跟著更新、其他視窗啟用後是否被系統重設），
    但已足以推翻「強制使用中渲染無效」的說法：這條公開訊息路線**尚未被證實無效**，屬待驗證
    的候選做法（補驗方式：以可控制的背景圖案在截圖之間變化，確認 A 的模糊內容跟著變）。
    另有一個純屬「做對照才會踩到」的坑一併記在探針檔頭與報告：
    `DwmSetWindowAttribute` 呼叫後若視窗尺寸/位置沒有跟著變，DWM 不一定會重新計算非用戶端
    渲染，探針原本因此誤判成「decorations(false) 失效、跑出原生標題列」，後來在
    `SetWindowPos` 加上純 no-op 的 `SWP_FRAMECHANGED` 才排除；這條在 Microsoft Learn 兩個
    函式頁都沒有明文寫，屬社群報告的實務作法（見報告檔的
    [PowerToys PR #749](https://github.com/MuyuanMS/PowerToys/pull/749) 一手佐證），非官方
    保證，日後若行為不同要重新驗證。
  - **結論**：失焦（小工具的常態）時毛玻璃不呈現——由預設行為的均勻色塊佐證；
    `host/src/desktop.rs::ACRYLIC_WORKS_UNFOCUSED_DEFAULT` 維持 `false`（原為探針未做前的
    保守預設，現由預設行為的實測結果佐證）；`resolve_appearance` 不必修改。`WM_NCACTIVATE`
    強制使用中渲染的效果尚未驗證為即時模糊，**在補驗完成前保守停用、不採用**（不代表已證實
    無效）。小工具外觀一律使用「純色」模式（design.md D8「桌面層行為集中在 desktop 模組」與 spec
    「小工具外觀模式」原訂的降級路徑）；毛玻璃選項在設定介面標示為不可用。4K 外接螢幕
    （3840×2160）於 2026-10-06 補驗，結果與筆電相同：失焦時測試組為不透明平面色塊、控制組
    半透明，圓角、無黑底與殘影（證據 `host/tools/evidence/1.2-*-ext4k.*`），符合「成因是視窗
    啟用狀態而非 DPI／解析度」的預期。

### D9. 位置模型

- `WidgetPlacement { monitor: MonitorId, col, row, w, h }`（整數格）。原本的 `anchor`、
  `dx`／`dy`、`scale` 移除：大小由格數決定，比例由格線決定。
- `MonitorId` 沿用 `Primary`（預設值，跟隨目前主螢幕）與 `Device(monitorDevicePath)`（穩定
  識別，`DisplayConfigGetDeviceInfo` 取得，**不含**解析度、**不用** `\\.\DISPLAYn`）。
  使用者更換主螢幕後，`Primary` 記錄可能與某個 `Device` 記錄落在同一台螢幕、彼此從未檢查過；
  這由下方推導的全域衝突處理吸收，不另做正規化。
- 設定版本 `SETTINGS_VERSION` 升為 2。版本判斷在 `merge_json` 補齊預設值**之前**、對原始 JSON
  做（否則缺少的 `version` 會被補成 2）；缺 `version` 或 `version < 2` 視同損壞：改名為
  `settings.json.bad-<時間>` 備份後以預設值啟動（舊的錨點距離換算成格子會有取整誤差與重疊，
  不做遷移；本 change 尚未發布，無外部使用者）。載入後逐一驗證格座標範圍
  （`w、h ≥ 1`、`col + w ≤ 48`、`row + h ≤ 48`），不合法的那個小工具在記憶體中退回它的預設格座標
  （下一次任何存檔時一併寫回）。
- 實際位置由純函式從「記錄位置＋目前顯示器清單」推出，記錄位置只在 D7 的兩條使用者路徑改寫：
  1. 每個開啟中的小工具對應到一台實體顯示器：`Device` 存在即該台，`Primary` 或 `Device` 不存在
     則主螢幕；格座標沿用記錄值。
  2. 每台顯示器分兩階段放置，優先序為「記錄就在這台」者先於「從別處換來」者，同級依註冊表順序：
     - 第一階段：依優先序只放記錄格子與已放置者不相交的小工具，相交者先跳過。單次掃描邊放邊找
       空位會讓找到的空位佔走排序較後、記錄本身合法的小工具，形成連鎖換位，所以分開。
     - 第二階段：依同一優先序替被跳過者依 D7 找空位（記錄格數→最小格數）；仍找不到則暫時隱藏，
       系統匣選單加一條停用項目標示「空間不足，暫時隱藏：<名稱>」（不引入通知 plugin）。暫時
       隱藏者不佔格。
  3. 原顯示器回來 → 重新推導，自然復位。
- 重新推導時機：顯示設定變更（解析度、縮放、拔插）、編輯版面放開成功、開啟或關閉小工具。
  重新推導後每個視窗的矩形與倍率都重設（換位的小工具可能因此移動，或因空間空出而重新出現）。
- 全部寫成純函式，單元測試以屬性測試涵蓋多種工作區尺寸×縮放比例（相鄰共用邊界、兩兩
  不相交、預設格座標不小於最小格數），以及對齊、彈回、找空位順序、`Primary` 與 `Device`
  撞同一台、拔除／接回、主螢幕空間不足、衝突者找空位不擠走記錄合法者、放開成功後重新推導
  位置不變。

### D12. 生命週期

- 單一執行個體：Tauri 官方 plugin。開機自啟以 `--autostart` 參數啟動，重新啟動註冊
  帶 `--restarted`；single-instance 回呼遇到這兩種參數時靜默忽略，只有手動啟動才開設定視窗。
- 開機自啟：登錄的是 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的 `fc-host` 值
  （`"<exe 路徑>" --autostart`，路徑加引號）。**初次登錄與移除歸安裝檔**（安裝時寫入、解除安裝
  時刪除，屬子專案 3）：宿主啟動——含設定檔首次建立——一律不碰登錄，開發建置的路徑不會被寫進
  使用者的開機自啟，驗收腳本以暫存 `%APPDATA%` 首次啟動也不會改到真正的登錄。宿主只在使用者於
  設定視窗**實際切換**「登入時自動啟動」時寫入（指向目前執行檔）或刪除 Run 值；修改其他設定不碰
  登錄。永不改寫 `...\Explorer\StartupApproved\Run`——使用者在工作管理員或「設定 > 啟動應用程式」
  的停用由系統保留。不用 `tauri-plugin-autostart`：它底下的 `auto-launch` 每次 `enable()` 都會把
  `StartupApproved` 改回啟用，且路徑不加引號。
- 開機自啟的顯示以登錄實況為準：設定檔的 `autostart` 預設維持 `true`（代表「預期已由安裝檔
  登錄」），但沒有安裝檔的開發建置會是「設定檔 `true`、登錄沒有值」。若照設定檔顯示，開關顯示
  「開」而登入時不會自啟，使用者還得先關再開才寫得進去。做法（最簡單且不誤導）：`get_settings`
  與 `update_settings` 回傳、以及**任何路徑**廣播的 `settings` 事件（設定更新、編輯版面切換、
  拖曳放開）的 `autostart`，一律換成「Run 值目前存不存在」；讀不到登錄時退回設定檔的值。
  `settings` 事件只能經單一入口（`widgets::emit_settings`）發出，由它套用登錄實況，靜態測試守住
  沒有繞過它的發送。`update_settings` 以這個實況當合併基準與「前值」，只有 patch 把開關切到
  與實況不同的值才寫登錄——設定檔與登錄不一致本身不觸發寫入，所以設定結構不用改、不新增欄位。
  寫登錄排在存檔之前：寫入或刪除失敗（例如企業原則鎖住 Run 機碼）時整筆回傳錯誤「無法寫入開機
  自動啟動設定」，設定檔、記憶體中的設定與登錄都不變、也不廣播，設定視窗顯示錯誤並把開關還原；
  寫入成功但存檔失敗時，把登錄改回原值後回傳存檔錯誤。設定檔裡的 `autostart` 因此只是讀不到
  登錄時的退回值，存檔時記下合併後（＝寫入後登錄實況）的值。查詢存在與否時帶 `RRF_NOEXPAND`，
  不展開 REG_EXPAND_SZ。取捨：只看 Run 值存不存在，不比對路徑是否指向目前的執行檔、也不讀
  `StartupApproved`——使用者在工作管理員停用時開關仍顯示「開」（系統層的停用由系統呈現），
  指向舊路徑的值也算已登錄（安裝檔會在重新安裝時覆寫）。
- 系統匣：Tauri 核心 tray 功能（`tray-icon` feature）。
- 暫停偵測：`SHQueryUserNotificationState` 每 5 秒輪詢，`QUNS_BUSY`、
  `QUNS_RUNNING_D3D_FULL_SCREEN`、`QUNS_PRESENTATION_MODE` 視為暫停，其餘不暫停；
  `WTSRegisterSessionNotification`（鎖定）；`RegisterPowerSettingNotification`
  （顯示器、電源來源、省電）。
- WebView2 故障：以 Tauri 的 `with_webview` → `PlatformWebview::controller()`／`environment()`
  （`tauri-2.12.0/src/webview/mod.rs:184-197`）取得底層 WebView2，用 `webview2-com`
  （`=0.39.1`，與 wry 同版）在每個小工具的 `ICoreWebView2` 上 `add_ProcessFailed`。探針 1.4
  實測（證據 `host/tools/evidence/1.4-*.log`，探針 `host/examples/probe_webview2.rs`）與據此的
  處理如下：
  - renderer 被終止：只有該 renderer 服務的視窗收到 `RENDER_PROCESS_EXITED`（reason
    `CRASHED`），其他視窗心跳不中斷；對事件來源的 `ICoreWebView2` 呼叫 `Reload()`，約 50 ms
    恢復。同源小工具在 3 個與 8 個視窗下都是一窗一 renderer、未共用；但官方文件說明 renderer
    可服務同一 user data folder 下多個 WebView，故不假設一對一——每個收到事件的 webview 各自
    `Reload()`，即自然涵蓋共用的情況。
  - browser process 被終止：每個 webview 各收到一次 `BROWSER_PROCESS_EXITED`（reason
    `UNEXPECTED`），須去重、只處理一次。此時 Rust 行程與 Tauri 視窗（HWND 存在且可見）都仍
    存活，但 WebView2 不會自行重啟：舊 webview 的 `Reload()` 回 `0x8007139F`、舊環境查詢行程回
    `0x80070015`，不處理則內容永久停擺。復原＝以同一 user data folder 先建立新一代全部小工具
    視窗、再 `destroy()` 舊視窗（先建後拆，避免視窗全關觸發結束；並在
    `RunEvent::ExitRequested` 的 `code` 為 `None` 時 `prevent_exit()`）。實測事件後約 1.3–1.7 秒
    （含刻意延遲 1 秒）新視窗恢復，新 webview 的事件訂閱照常有效。
  - GPU process 被終止：所有 webview 收到 `GPU_PROCESS_EXITED`，browser 約 2 秒內自動重啟
    GPU process、頁面心跳不中斷；只記錄、不處理。
  - `RENDER_PROCESS_UNRESPONSIVE`：官方定義為 renderer「對使用者輸入無回應」；頁面 JS 無窮
    迴圈 40 秒、期間無輸入時從未觸發，而小工具鮮少收到輸入，不能依賴。改以核心看門狗偵測
    卡死：核心每 5 秒對每個小工具 `ExecuteScript` 一段只回傳記號的探測腳本（Tauri
    `eval_with_callback`），完成回呼帶回記號才算活著；**暫停原因集合為空時才計時**（暫停中
    不探測、逾時計數歸零），**連續 3 次**無回應（頁面連續 15 秒以上沒執行過任何腳本）才判定
    卡死，銷毀並重建該小工具視窗。不採探針 1.4 的「頁面計時器→核心」心跳：小工具被一般視窗
    遮住時瀏覽器會節流頁面計時器（最慢約每分鐘一次），頁面心跳會把被遮住的正常小工具誤判
    為卡死；`ExecuteScript` 不是頁面計時器、不受此節流，頁面 JS 真的卡死時則排不上主執行緒、
    回呼不來。同一小工具 10 分鐘內自動重建上限 3 次（防一載入就卡死的無窮重建）。實測（task
    5.6）注入無窮迴圈後約 20 秒判定、重建約 0.1 秒，卡住的 renderer 隨之結束。收到
    `UNRESPONSIVE` 事件時同樣重建該視窗（官方範例對無回應建議重建而非 `Reload()`）。
  - 重建視窗的 label 為 `w-<id>-r<n>`（先建後拆期間新舊並存，label 須唯一），一律經 3.1 的
    視窗工廠建立；頁面載入後自行 `subscribe_data`＋`get_snapshot`＋`get_pause` 恢復資料與
    暫停狀態。
- 重新啟動註冊：啟動時呼叫 `RegisterApplicationRestart("--restarted", …)`；使用者從系統匣結束
  時先 `UnregisterApplicationRestart`。依 Microsoft Learn，當機後的重啟需使用者同意、自動重啟
  只發生在經 Restart Manager 關閉並由其要求重啟時，規格據此撰寫。
- 記錄：本機檔案、每日輪替、保留 7 天。
- 設定檔：`%APPDATA%\tw.fintools.fc-host\settings.json`，含 `version` 欄位供日後升級；解析失敗時
  改名為 `settings.json.bad-<時間>` 後以預設值啟動。

## Risks / Trade-offs

- [Win+D 偵測未驗證，spike 已見 z-order 來回切換] → 探針 1.1 先做，含「點桌面」反例；若判準
  不可行，退路為進入顯示桌面時小工具暫時隱藏、離開後恢復，並先回報使用者決定。
- [DWM Acrylic 可能只在視窗取得焦點時呈現，而小工具永不取得焦點] → 探針 1.2 在點過其他應用程式
  之後截圖驗證；不成立則毛玻璃停用、改純色（使用者已決定不採用未公開 API）。
- [`focusable(false)` 可能影響觸控或精準觸控板捲動] → 探針 1.3（見上方 D8）：切換置底旗標後
  `WS_EX_TOOLWINDOW`／`WS_EX_NOACTIVATE` 仍在、Alt+Tab 判準穩固，**點擊不搶焦點與滑鼠滾輪
  捲動已於 2026-09-28 A 節注入驗收完成，皆 PASS**（見上方 D8 段落）。觸控板兩指捲動、觸控
  螢幕拖曳仍為人工項目，見 `.superpowers/sdd/tasks/human-checklist.md`「Task 1.3」節；
  `WM_MOUSEACTIVATE` 改攔退路目前判斷不需要（外部可觀察行為已通過，見 D8 附帶發現）。
- [同源 WebView 可能共用 renderer，單一 renderer 故障會影響多個小工具] → 規格已改為「所有受影響
  的小工具」恢復；探針 1.4 實測同源 3／8 個視窗皆一窗一 renderer，復原仍以「各 webview 依自己
  收到的事件處理」寫成，不依賴此觀察。
- [48 格在小螢幕上一格只有約 18 邏輯像素高、30 邏輯像素寬] → 對齊精度以「佔工作區比例」為準，
  不追求像素級微調；預設格座標以實機截圖調整，唯一清單在 `settings.rs` 的預設格座標。
- [倍率小於 1 時文字變小] → 倍率下限 0.5，最小格數據此計算；使用者可自行拖大。
- [`startResizeDragging` 在沒有 `WS_THICKFRAME` 的視窗上能否進入尺寸迴圈、是否搶焦點]
  → task 7.6 探針實測不能進入，已改採 D7 退路（編輯版面期間切 `WS_SIZEBOX`）；調整期間前景與
  焦點不變已實測（見 D7「調整大小的機制」）。
  （在父視窗 `WM_NCHITTEST` 回傳邊緣命中碼不可行：WebView2 子視窗蓋滿用戶區，父視窗收不到。）
- [倍率只看寬度，寬螢幕的可用高度較少] → 時鐘沒有捲動區，高度不足會被裁切；預設格座標以高寬比
  ≥ 0.53 為準並由屬性測試守住，更寬的螢幕由使用者拖大。
- [多個 WebView2 視窗的記憶體] → 共用同一環境；24 小時實測，記憶體增幅須低於 20%。
- [顯示邏輯搬移出錯導致數字不一致] → D11 對照測試為完成條件，未通過不得宣稱完成。
- [被完全遮住的 WebView2 可能節流計時器，影響 04:00 翻日準時度] → 解除遮蔽時頁面立即重算；
  6.1 實測記錄。

## Migration Plan

1. 本 change 期間 Lively 版照常運作，排程與資料層不動；使用者在設定中把資料目錄指向資料層輸出夾
   （本機 `D:\finance-calendar`）。
2. 使用者自行開啟宿主並行觀察；確認穩定後再從 Lively 移除桌布。
3. 回退：結束宿主並關閉自動啟動，Lively 版不受任何影響。
4. 正式安裝與自 Lively 版遷移的使用者流程在子專案 3 處理。
